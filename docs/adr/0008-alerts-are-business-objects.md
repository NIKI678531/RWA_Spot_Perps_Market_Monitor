# 告警是业务对象，不是通知

v2.0 的异常页是一条技术流水：检测器名、severity、时间、证据。它能回答「系统发现了什么」，
回答不了「然后呢」。没有 owner、没有业务备注、没有判误、没有研究任务、没有结论与复盘——
一条没人负责的告警，第二天就等于没有发生过。

更实际的问题是：如果不知道哪些告警最后被判定为误报，阈值就永远无法校准。
误报率是要被追踪和下调的指标，而它只能由人的判断产生。

决定：`alert` 是一个有状态机、有 owner、有审计的业务对象。

```
DETECTED ──(发布门)──> TENTATIVE ──(第 2 次确认)──> PUBLISHED
                                                      │
                          CLAIMED ──> IN_REVIEW ──> ACTIONED ──> RESOLVED
                          任意阶段 ──> FALSE_POSITIVE | DISMISSED（须记录原因）
```

- `DETECTED` 只存在于系统内部，永不出现在界面或 API 响应中。
- 状态不是一个被更新的字段：它是 `alert_action` 动作流的物化视图，可以完整重放。
- 每次迁移、备注、转派与 `audit_log` 同事务写入。审计写失败则整个动作失败。
- `RESOLVED` 前必须有复盘：最终结论、是否真实需求、影响了什么决策、误报原因、阈值建议。
- `FALSE_POSITIVE` 与 `DISMISSED` 是两回事：前者是系统判断错了，后者是系统对了但业务选择不动。
  混为一谈会让误报率这个指标失去意义。

## Consequences

- 数据修复不覆写历史告警。修好数据后要么给原告警追加一个证据版本，要么产生一条新告警——
  昨天基于错误数据发出的告警，历史上确实发生过，抹掉它就抹掉了改进的依据。
- `research_task` 与 `issuance_candidate` 通过 `alert_id` 反向关联到触发它们的告警。
  「信号 → 研究任务转化率」这个成功指标只有在这条关联存在时才是可算的。
- 引入了权限模型：谁能认领、谁能关闭、谁能改阈值。这是产品复杂度的实质增加，
  但一个不知道谁在负责的工作队列，本质上还是一条流水。
- 通知（应用内、邮件、R2 的 Teams/Slack）只是入口。处理动作一律回到系统里做并写审计，
  否则结论散落在邮件回复里，复盘时无法归集。
