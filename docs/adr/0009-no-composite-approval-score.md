# 任何分数都不批准任何事

把需求强度、持续性、跨所一致性、数据质量和可行性合成一个 0–100 的「发行就绪度」，
是这类系统最自然的下一步，也是最容易造成实际损害的一步。

三个理由：

1. **合成需要权重，而权重没有依据。** 需求强度与合规可行性之间没有汇率。
   任何一组权重都是拍出来的，但输出的是一个看起来经过计算的数字。
2. **合成会跨口径相加。** 现货成交、永续 OI、跨所覆盖数、Raw/Adjusted 差异是不同量纲的东西，
   标准化之后相加，正是本项目从第一天起就在代码层面禁止的操作，只是换了一层皮。
3. **分数会替代判断。** 一旦有了 82 分和 79 分，讨论就变成「为什么它只有 79」，
   而不是「渠道那边有没有人真的问过这个标的」。

决定：系统负责**发现、排序、保全证据**；批准由人做，且在系统之外的评估门里做。

- severity、热力图色阶、四象限位置只用于**排序与优先级**，不作闸门。
- 需求证据热力图的列各自独立标准化，**不得横向求和**；界面上不出现总分列。
- 发行候选在五道评估门（发现 → 数据确认 → 小规模验证 → 可行性评估 → 产品委员会）之间移动，
  只能通过写进 `candidate_gate_log` 的人工决策，每道门有进入条件、降级条件、owner 与产出物。
- UI 不得出现任何暗示自动批准的措辞。

## Consequences

- 前端图表组件增加 `assertNoRowTotal()` 断言：矩阵与热力图不得出现跨列合计。
  规则写进代码，因为「加一列总分」在任何一次迭代里都会被当成小改动提出来。
- 排序仍然需要一个序。用 severity 与绝对量排序是可以的——排序错了代价是看晚一点，
  批准错了代价是发了一个没人要的产品。两者的容错完全不同。
- R3 的「阈值自适应建议」与「产品机会回测」同样受此约束：模型可以建议阈值，
  不可以决定候选是否通过评估门。
- 代价：管理层可能仍然想要「一个数字」。给的替代品是四问卡的结构化答案
  ——答案、变化、证据、反证、信心——它更长，但每一项都能被追问到底。
